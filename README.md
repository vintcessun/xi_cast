# xi_cast —— 一块 ESP32-S3，一上电就自动把戏曲投到电视上

插上电，等十几秒，电视上就开始放《斗阵来看戏》。不用手机、不用遥控器、
不用人管；放完一集自动下一集，放完一部自动换一部。

这是上位机项目 [`getvideo`](https://github.com/vintcessun/getvideo) 的嵌入式版本。那边是电脑上跑的
命令行程序，要开着电脑；这边是一块几十块钱的板子，插在电视旁边的 USB 口上
就行。

## 硬件

* 一块 ESP32-S3 开发板（DevKitC-1 之类，4MB 以上 flash 都行）
* 一根 USB 线供电

**不用接任何外设**。视频不经过板子 —— 板子只是把视频地址递给电视，
真正下载和播放的是电视自己。所以板子只要能连上 WiFi 就够了，
连视频解码都不需要。

## 跑起来

### 一、先在电脑上跑（开发板还没到货也能玩）

固件里的逻辑和电脑上跑的是**同一份代码**（见下面「怎么做到的」），
所以可以先在电脑上验证一遍：

```powershell
# 全套自动化测试：协议、flash、掉电、投屏全流程
cargo test

# 真的投到家里的电视上（会去 xmtv 拉节目、在局域网里扫设备）
cargo run -p xi-cast-sim

# 扫不到设备时，直接指定设备地址
$env:XI_CAST_TV_URL = "http://192.168.1.20:8200/rootDesc.xml"
cargo run -p xi-cast-sim
```

不想打扰家里人看电视的话，可以先拿假电视试：

```powershell
cargo run -p xi-cast-sim --bin mock-tv     # 窗口 1，会打印设备地址
$env:XI_CAST_TV_URL = "<上面打印的地址>"
cargo run -p xi-cast-sim                   # 窗口 2
```

### 二、烧到板子上

**第 1 步，填 WiFi**（这一步不做的话固件开机会直接报错）：

```powershell
cd firmware
copy wifi.toml.example wifi.toml
# 用编辑器打开 wifi.toml，填上自家 WiFi 的名字和密码
```

`wifi.toml` 在 `.gitignore` 里，不会被提交上去。

**第 2 步，烧录**（一条命令搞定，同时看日志）：

```powershell
cd firmware
cargo build --release
espflash flash --partition-table partitions.csv --after hard-reset --monitor `
  target/xtensa-esp32s3-none-elf/release/xi_cast
```

分区表里比默认多了一个 512KB 的 `xicast` 数据分区，节目目录就存在里面。
`--partition-table` 每次都带上最省心（重烧应用不会动到数据分区，
已经存下来的节目一条都不会丢）。

**日志走串口，不用调试器。** 板子插原生 USB 口（设备管理器里显示
`USB JTAG/serial debug unit`）就行，同一根线既烧录又出日志。

> 这里踩过一个坑：模板默认用 `defmt` + RTT，配 `probe-rs run`。
> 在这块板子上烧录一切正常，但 **RTT 一个字都读不出来** —— 等于没有日志，
> 连 panic 都看不见。所以整个固件改成了 `esp-println` 打串口。
> 另外 `init_logger_from_env()` 的等级来自编译期的 `ESP_LOG` 变量，
> 没设就是「全关」，也是一条日志都不出来；现在改成显式指定 `Info`。

### 三、板子发、电脑收（联调用）

把电脑变成一台**局域网里真能被搜到的**假电视，让板子投给它 ——
这样不用碰家里的电视也能验证整条链路：

```powershell
# 参数是本机网卡 IP（不是 127.0.0.1，板子要连得上）
cargo run -p xi-cast-sim --bin mock-tv -- 192.168.0.105
```

它会绑 1900 端口收 SSDP、8200 端口提供设备描述，然后把板子投过来的每一集
都打出来。第一次跑 Windows 防火墙会弹窗，**专用和公用网络都要勾**。

> 1900 端口在 Windows 上被系统的 SSDPSRV 服务占着，所以用了 `SO_REUSEADDR`
> 和它共享 —— 这是 getvideo 那边就记录过的坑。

## 它是怎么工作的

```
   上电
    │
    ├─ ① 打开 flash 目录        几十毫秒，不联网
    │      有节目 → 直接往下走；空的（第一次开机）→ 待会儿先拉几页
    │
    ├─ ② 连 WiFi + DHCP
    │
    ├─ ③ 找电视
    │      上次那台还在吗？ ── 在 ──▶ 用它（几十毫秒）
    │           └── 不在 ──▶ SSDP 扫描（几秒）
    │
    ├─ ④ 增量更新节目           一般只新增一条
    │
    └─ ⑤ 随机挑一部戏，一集接一集地投，直到断电
           └─ 空隙里顺手把历史节目往回补
```

节目数据来自厦门卫视的两个接口（都是 **http，不用 TLS**，这是整个方案
能塞进 ESP32 的前提）：

| 用途 | 地址 | 实测要点 |
| --- | --- | --- |
| 节目列表 | `mapi1.kxm.xmtv.cn/api/open/xiamen/web_search_list.php` | chunked 传输、中文 `\uXXXX` 转义、按发布时间倒序、`offset` 分页正常 |
| 分享页 | `share1.kxm.xmtv.cn/xmtv/<日期>/<16位id>.html` | 43KB，视频地址在第 5712 字节；**不带浏览器 User-Agent 会被 CDN 的 WAF 回 418** |

视频本身是 `https://vod1.kxm.xmtv.cn/....mp4`，https 只有电视需要处理。

## 三个设计上的要点

### 一、flash 上的目录是「只追加」的

上位机那边是一个 436KB 的 JSON（`data.txt`），每次更新都全量拉 2291 条、
和旧的比一遍、整个文件重写。搬到板子上这么干有三个问题：全量 2.3MB 每次
开机都要拉一遍；整份重写要把分区全擦全写一遍，白白磨损 flash；重写到一半
掉电，数据就全没了。

所以换成只追加的日志（`core/src/store.rs`）：

```
 ┌──────────── bank 0（分区的前一半，256KB）────────────┐
 │ 头(16B) │ 记录 │ 记录 │ 记录 │ …… │ 0xFF 0xFF 0xFF   │
 └───────────────────────────────────────────────────────┘
 ┌──────────── bank 1（整理的时候才用）─────────────────┐
 └───────────────────────────────────────────────────────┘

 一条记录：
   ┌──────┬──────┬─────────────┬──────────────┬───────┬──────┐
   │ 类型 │ 标志 │ 长度 n (LE) │ 负载（补齐 4）│ CRC16 │ 填充 │
   └──────┴──────┴─────────────┴──────────────┴───────┴──────┘
```

* 全部 4 字节对齐 —— ESP32 flash 的写入粒度就是 4 字节；
* 类型 `0xFF` 就是「这里还是擦除态」，也就是日志末尾，
  **不需要单独维护写指针**，开机扫一遍就知道；
* 一条节目 48 字节，全部 2291 条约 110KB，只用掉一个 bank 的 43%；
* 新节目在末尾接一条，**已经写过的字节一个都不动**。

一条节目记录里存的是 id、发布时间、分享页日期、16 位分享 id、剧目名。
特意**不存完整的分享地址**（省 40 字节 × 2291 条），也特意**不用发布时间
去推算分享页日期** —— 全量数据里有 91 条对不上，推出来的地址是 404。

掉电怎么办：

* 每条记录带 CRC，写到一半掉电留下的半截记录校验一定过不了；
* 开机扫到坏记录就停下，把前面的好记录整理到另一个 bank，坏的连同后面
  一起丢掉；
* bank 头是**整理完成之后最后才写**的 —— 整理到一半掉电，新 bank 没有头
  就是无效的，老 bank 原封不动，数据一条不少。

效果：一天新增一条节目的话，**很多年都不会触发一次擦除**。

### 二、记住上次那台电视

SSDP 扫描要好几秒（还得分几轮重发对抗组播丢包），而直接问一台已知地址的
设备只要几十毫秒。所以扫到之后把设备地址写进 flash，下次开机先试它，
连不上（路由器重启、DHCP 换了 IP）才退回去扫描。

设备发现这块的坑全部来自上位机项目的实战（`core/src/ssdp.rs` 里有详细注释）：

* 只发一种搜索目标会漏设备 —— 很多国产盒子只认 `ssdp:all`，
  这就是「手机能投屏，程序却扫不到」的原因，所以四种全发一遍；
* 组播允许丢包，一次只发一个包等于没搜，所以分三轮重发；
* 同一台设备会以多个身份回应，要按 USN 里的 uuid 去重，不然一台电视
  会被当成好几台。

### 三、ESP32-S3 的 cache 问题

代码是**从 flash 直接执行**的（XIP，靠指令 cache 加速），而写 flash 的时候
cache 必须先关掉。关掉的那段时间里，任何从 flash 取指令或取数据的行为
都会当场炸掉。

esp-storage 把写操作放进 IRAM 并关中断，所以**执行写操作的那个核**是安全的。
但另一个核不安全 —— ESP32-S3 是双核，第二个核如果正在从 flash 取指令，
一次 flash 写就能让它跑飞。esp-storage 默认的做法是发现另一个核在跑
就**直接让写失败**。

这个固件的对策是**根本不启用第二个核**：esp-rtos 只跑核 0，WiFi、网络栈、
投屏全是一个 executor 上的 async 任务。配套的两点：

* **写要小块**：目录是一条记录一次写（几十字节），不攒批 ——
  cache 关着的时候 WiFi 收不了包；
* **第一次开机的整块擦除放在联网之前**：擦一个 256KB 的 bank 是 64 个扇区，
  累计几百毫秒 cache 反复关着，这时候还没连 WiFi，没有连接会因此断掉。

细节写在 `firmware/src/storage.rs` 的模块注释里。

## 占多少资源

release 构建实测：

| | 大小 | 说明 |
| --- | --- | --- |
| 烧录镜像 | 555 KB | 分区给了 3 MB，用掉 18% |
| `.bss` | 82 KB | 主要是投屏任务的 future（里面有 8KB 的设备描述缓冲）和网络栈 |
| `.data` | 10 KB | |
| 堆 | 100 KB | esp-radio 要的，照抄官方 wifi 例子的配置 |
| flash 数据分区 | 512 KB | 存满 2291 条节目只用 110 KB |

ESP32-S3 有 512KB SRAM，剩下的余量很宽。

## 目录结构

```
core/       投屏逻辑本体。no_std、不分配内存、不知道自己跑在哪
  ssdp.rs     找设备
  upnp.rs     读设备描述
  soap.rs     拼投屏指令
  http.rs     极小的 HTTP/1.1（含 chunked）
  xmtv.rs     节目列表和分享页的流式解析
  store.rs    追加式 flash 目录
  net.rs      平台要提供的网络能力（trait）
  app.rs      整机流程

firmware/   ESP32-S3 固件。只做两件板子特有的事：
  net.rs      把 embassy-net 接到 core 的 trait 上
  storage.rs  从分区表里找到数据分区
  bin/main.rs 开机流程

sim/        电脑上的那一套：假电视、假 xmtv、假 flash、真 tokio
fixtures/   从真服务器抓下来的原始报文，测试直接拿它当输入
```

`firmware/` 故意**不是**工作区成员：它自带 `.cargo/config.toml`，
里面写死了交叉编译的目标和链接参数，进了工作区的话根目录 `cargo test`
会被这些参数带跑偏。

## 没有开发板，怎么保证它是对的

这是这个项目最花力气的地方。做法是：**把所有会出错的逻辑放进 `core`，
让它同时能在板子上和电脑上跑**，然后在电脑上把它测穿。

```powershell
cargo test        # 147 个用例，十几秒跑完
```

测的不是仿写的一份，就是上板要跑的那一份。覆盖的东西包括：

**协议层**（用 `fixtures/` 里从真服务器抓下来的报文当输入）
* 真实的 20 条节目、翻页、2020 年那批格式不一样的老记录；
* 响应被 TCP 切成 1 / 7 / 300 / 512 字节各种大小都要解得一模一样
  —— 电脑上回环一次读几 KB，板子上 WiFi 是几百字节一片，
  这类 bug 只有主动切碎了才测得出来；
* chunked 的长度行被切在中间；
* SOAP 的双层 XML 转义、设备声明 `AVTransport:2/:3` 时的版本跟随；
* 半截的、乱码的、被 WAF 拦掉的响应，一律不能 panic。

**存储层**（跑在一块**较真的**假 NOR flash 上：写只能把 1 变 0、
擦除按扇区、读写按 4 字节对齐，违反了直接报错）
* 写到一半掉电留下的半截记录会被丢掉，而且后面还能接着写；
* 中间某条被改了一个位，CRC 要拦下来；
* bank 写满自动整理、整理到一半掉电老数据一条不少；
* 重启之后节目、设备、进度都还在；
* 追加时**已写过的字节一个都没变**（这是「追加式」的全部意义）。

**整机流程**（假电视会真的回应 SSDP、真的处理 SOAP、真的按查询次数
报告播放结束）
* 冷启动 → 拉节目 → 找电视 → 解析直链 → 投出去 → 播完换下一集；
* 第二次开机不重新下载、不重新扫描（把 SSDP 指向死端口来证明）；
* 电视换了 IP → 自动退回扫描并记住新地址；
* 电视中途关机 / 接了连接却一声不吭 → 超时、退避、重新找设备，不卡死；
* xmtv 挂了 → 用 flash 里的缓存照样投。

另外，`cargo run -p xi-cast-sim` 已经在电脑上对着**真实的** xmtv 接口
跑通了整条链路：拉到 100 条节目 → 找到设备 → 解析出真实的 mp4 地址 →
一集接一集投出去；后台补历史把目录补到 540 条；重启之后 1 秒内直接开播，
一条都没重新下载。

## 怎么换一部戏

**按一下板子上的 reset 键。** 每次开机都会重新随机挑一部，所以复位就是换台。

平时不用管它：一部戏按集数顺序放完之后，会自动再随机挑一部接着放，
一直循环下去。随机是「有放回」的，理论上可能连着抽到同一部，
全库 276 部，概率很低；集数多的大戏更容易被抽中（这是故意的，
一部 41 集的《柳君拂》比一场一集的晚会更该被放到）。

## 上板实测（2026-09-05）

板子：ESP32-S3 rev0.2，16MB flash。接收端是电脑上的假电视
（`192.168.0.105:8200`）。串口日志原样摘录（WiFi 名字和 AP 的 MAC 已打码）：

```
INFO - flash 目录就绪：660 条节目，229272 字节空闲，第 1 代
INFO - WiFi 已连上: ssid: "<家里的WiFi>", channel: 6, authmode: Wpa2Personal
INFO - 拿到 IP: 192.168.0.106/24 网关 Some(192.168.0.1)
INFO - flash 里已经有 660 条节目，直接开播
INFO - 先试上次那台设备: http://192.168.0.105:8200/desc.xml
INFO - 上次那台还在: FastCast 客厅电视
INFO - 这部放《龙凤环》，一共 8 集
INFO - 投第 1 集: https://vod1.kxm.xmtv.cn/video/2025/04/19/1d5e....mp4
```

重启一次之后：

```
INFO - flash 目录就绪：1440 条节目，190668 字节空闲，第 1 代
INFO - flash 里已经有 1440 条节目，直接开播
```

对应验证到的是：

| 要求 | 证据 |
| --- | --- |
| 板子连 WiFi | `WiFi 已连上` + 拿到 192.168.0.106 |
| 节目表自动更新、写进 flash | 660 → 1440 条，跨重启保留 |
| 下次开机是增量，不从头下 | `已经有 1440 条节目，直接开播`，接口只翻一页 |
| 自动找设备 | `先试上次那台设备` 直接连上，没走 SSDP |
| SSDP 扫描本身可用 | flash 里那个地址只可能是某次扫描扫出来写进去的 |
| 真实投屏 | 接收端收到 6 集，全是从真 CDN 解析出的 mp4，按集数顺序 |
| 自动切集 | 接收端报「播完」后板子自动投下一集 |

### 换成真电视之后（同一天）

配置改成 `tv_ip = "192.168.0.100"`（只问它一台，不广播）：

```
INFO - flash 目录就绪：2293 条节目，144964 字节空闲，第 1 代
INFO - 192.168.0.100 没应答单播搜索，改试几个常见的设备描述地址
INFO - 找到电视: 客厅电视 @ http://192.168.0.100:49152/description.xml
INFO - 这部放《母子河》，一共 12 集
INFO - 投第 1 集: https://vod1.kxm.xmtv.cn/video/2020/07/04/995c....mp4
```

电视上确认**画面正常播放、播完自动切下一集**。于是两件事有了结论：

* **mp4 直链这条路这台电视认**，`cast_share_page` 那个兜底开关用不上；
* 这台电视（HappyCast）**不应答单播 M-SEARCH**，靠「试常见端口」兜住了，
  第一个 `49152/description.xml` 就命中 —— 所以那份兜底列表是必要的，
  不能只做单播搜索。

目录也在这天补齐到了 **2293 条**（接口报的总数是 2291），全库拿下。

## 配置

固件的配置在 `core/src/app.rs` 的 `Config` 里，默认值适合家用：

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `fixed_ip` | 无 | **推荐**。只认这个 IP 上的设备，绝不广播扫描（也就绝不会投到邻居家） |
| `preferred_name` | `FastCast` | 走扫描时按名字挑。指定了 `fixed_ip` 就用不上 |
| `scan_ms` | 2500 | 一轮 SSDP 等多久 |
| `poll_ms` | 2000 | 多久问一次「放完了没」。不能太快，便宜盒子会被问死 |
| `first_pages` | 5 | 第一次开机拉几页（100 条）就开播，剩下的慢慢补 |
| `cast_share_page` | `false` | 投分享页地址而不是解析出来的 mp4 |

模拟器可以用环境变量调：`XI_CAST_TV_URL`、`XI_CAST_DEVICE_NAME`、
`XI_CAST_POLL_MS`、`XI_CAST_SHARE_PAGE`、`XI_CAST_FLASH`。

### `cast_share_page` 是干嘛的

默认行为是去分享页里把 `<source src="....mp4">` 抠出来，把 **mp4 直链**
投给电视。上位机项目的做法不一样，它直接把**分享页地址**（一个 .html）
投过去。

家里那台盒子到底认哪一种，没有板子和电视是没法确定的。所以两条路都留着：
如果上板之后发现「投过去了但电视没动静」，把这个开关打成 `true` 再试。
固件里也有对应的提示 —— 连着三集设备收下了地址却没进入播放状态时，
日志里会直接告诉你去试这个开关。

## 排查

**连不上 WiFi**

先看开机日志里那段扫描 —— 它把周围每个 AP 的 BSSID、信道、信号、加密方式
都打了出来，带 ★ 的就是目标：

```
INFO - ★ <家里的WiFi> aa:bb:cc:11:22:33  信道 6  -51dBm  Some(WpaWpa2Personal)
```

* **看不到 ★**：ESP32 只支持 2.4G，确认路由器的 2.4G 射频开着、这个 SSID
  在 2.4G 上也广播；
* **看得到 ★ 但连不上**：看紧跟着的失败原因。真机上遇到过一次
  `NoAccessPointFoundInAuthmodeThreshold` —— 意思是「AP 找到了，但它的加密
  档次低于我设的门槛」。`StationConfig::auth_method` 是**最低门槛**不是
  「我支持哪些」，档次顺序是 Open < WEP < WPA < WPA2 < WPA/WPA2混合 <
  WPA3 < WPA2/WPA3混合。当时把门槛设成了 `Wpa2Wpa3Personal`，而路由器是
  WPA/WPA2 混合，于是被固件自己滤掉了。用默认的 `Wpa2Personal` 即可，
  它对 WPA2 和 WPA/WPA2 混合都放行；
* **连上一会儿又断**：如果路由器把 2.4G 和 5G 合成了一个 SSID，
  band steering 可能在把板子往 5G 上赶。把 ★ 那一行的 BSSID 填进
  `wifi.toml` 的 `bssid=` 重新编译，板子就只认那个射频 ——
  **不用改路由器任何设置**。省电模式固件里已经关掉了（也是这类症状的常见原因）。

**扫不到设备**
1. 板子和电视是不是同一个 WiFi、同一个网段；
2. 路由器有没有开 AP 隔离、有没有禁掉组播（这两个一开，SSDP 根本出不去）；
3. 电视的投屏功能开了吗（有的电视要在设置里手动打开 DLNA / 多屏互动）；
4. 实在扫不到就直接指定：把电视的设备描述地址填进 `wifi.toml` 的 `tv_url=`。

**投过去了但电视没反应**
看 RTT 日志里有没有「连着 N 集都没真正播起来」那一条 —— 有的话多半是
盒子下载不了 https 的视频，把 `cast_share_page` 打开再试。

**开机报「打不开数据分区」**
分区表没烧对。用上面那条带 `--partition-table partitions.csv` 的
`espflash flash` 命令重烧一次。

**编译时警告「没有找到 WiFi 配置」**
`firmware/wifi.toml` 没建。复制 `wifi.toml.example` 填上就行。

## 已知的取舍

* **分享页主机名是写死的**（`share1.kxm.xmtv.cn`）。全量 2291 条记录
  用的都是它，所以 flash 里只存路径不存主机，一条省 40 字节。
  哪天 xmtv 换域名，这里要跟着改。
* **随机挑戏是按「集」等概率的**，不是按「部」。也就是集数多的大戏更容易
  被挑中 —— 家里放戏曲要的就是这个，一部 41 集的《柳君拂》比一场一集的
  晚会更该被放到。
* **整理 flash 时会丢掉视频直链缓存。** 它只是省一次 HTTP 请求，
  为了保留它多写一套「哪些还有用」的判断不划算。
* **不校时。** 整个流程不需要知道现在几点：增量更新靠「翻到已经存过的
  那条就停」，不靠日期比较。少一个 NTP 就少一个开机时的失败点。
